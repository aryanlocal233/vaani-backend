Vaani — Mela Help-Desk Communication System

Cache first, AI second: a knowledge-first architecture for high-volume help desks

A pilgrim speaks in their own language. Vaani detects it, understands the request, and answers from a cached, authority-approved knowledge base whenever possible — reaching for paid STT/translate/TTS APIs only for what hasn't been asked before.

1 Accuracy→ 2 Safety→ 3 Response speed→ 4 Cost efficiency→ 5 Simplicity→ 6 Scalability

01 Production architecture

Grounded in what's actually deployed today (single VPS, FastAPI, Docker, Sarvam AI, nginx+TLS) rather than a greenfield rewrite — this extends the running system in place.

04 API design

The existing binary WebSocket protocol (/ws/translate/{src}/{tgt}, frame flags 0x00–0x03) is unchanged for backward compatibility. New fields ride inside the existing JSON text frames; new endpoints are added alongside for admin/ops.

EndpointPurpose
WS /ws/translate/{src}/{tgt}Existing pipeline. JSON transcript/translation frames gain optional intent, confidence, cache_hit fields — additive, old clients ignore unknown fields.
POST /admin/faqCreate/update a FAQ entry (canonical question, answer, category, keywords). Triggers re-embedding + cache invalidation for that faq_id.
POST /admin/faq/{id}/approveMarks a draft FAQ approved; only approved entries are eligible for auto-answer.
GET /admin/analytics/summaryAggregates for the dashboard: cache-hit rate, API cost, cost avoided, per-counter/per-language breakdown.
GET /sync/bundle?since={version}Offline pre-cache bundle (top-N FAQs + translations + audio URLs) for device sync — see §7.
POST /devices/registerIssues a per-counter device token — see §8.

05 Semantic matching strategy

Exact-string matching (what's live today) is replaced by a three-stage match, cheapest first:

1 · Normalized exact

Lowercase, strip filler words/punctuation, check against question_variants.normalized_text. Free, in Redis, sub-millisecond.

2 · Keyword/alias

Today's approach (per-language keyword lists) as a fast pre-filter before vector search — cheap and catches the bulk of repeat phrasing.

3 · Vector search

Multilingual sentence embedding (e.g. intfloat/multilingual-e5-large or Sarvam's own embedding endpoint once available) + pgvector cosine search across question_variants.embedding, filtered to approved FAQs only.

Confidence thresholds (tune with production data, not fixed permanently):

ConfidenceAction
≥ 0.90Auto-answer from cache — no LLM/NMT call.
0.75 – 0.90Deterministic re-check (category TTL, keyword overlap) before answering; flagged as lower-confidence in analytics.
< 0.75Fall through to full STT→NMT→TTS pipeline, or route to operator for emergency-category intents (see §11 risk table).

A successfully-matched new phrasing is stored as another question_variants row (learning question wording) — the canonical_answer itself is never auto-edited by usage patterns (§14 of the original brief).

06 Language detection strategy

Sarvam STT's auto-detect (already in use, language_code="unknown") remains the primary signal — no manual language picker. Detected language + confidence is logged per request. Below a confidence floor, Vaani asks the speaker to repeat rather than guessing (never silently answer in the wrong language). Code-mixed speech (Hinglish, Tamil+English) is handled by Sarvam's STT as-is; normalization in the matching layer (§5) strips common English loanwords before the keyword/embedding stage so mixed phrasing still matches Hindi/regional intents.

07 Offline / degraded-mode architecture

flowchart LR
    pre["Pre-mela sync\n(top 100-500 FAQs)"] --> device["On-device SQLite\ntext + audio files"]
    device --> app["Vaani Android app"]
    app -- "online" --> api["Vaani API"]
    app -- "offline" --> device
    app -- "connectivity restored" --> sync["Analytics sync\n(queued requests)"]
    sync --> api

Before deployment, the top 100–500 expected questions (approved answers, translations, pre-generated audio for the mela's expected language mix) sync to the device via /sync/bundle into a local SQLite store. On connectivity loss, the app falls back to this local store for FAQ-category questions only — never for location-sensitive, time-sensitive, or emergency categories, which require live/authority-verified data. The UI clearly shows an "Offline mode" indicator. Queued analytics events sync once connectivity returns.

08 Cost-optimization architecture

Three cache levels, each skipping progressively more paid API work:

Level 1 — Text cache

Reuse a previously-approved answer's text. No NMT call.

Level 2 — Translation cache

Per (faq_id, language) translated answer, versioned. Re-translated only if the canonical answer changes.

Level 3 — Audio cache

Per (faq_id, language, voice, version) synthesized PCM. No TTS call on repeat — this is the biggest saver, since TTS is billed per character every time otherwise.

This is the same principle the currently-deployed FAQ layer already proved: a repeat question answered in 3ms with zero TTS call, versus ~5–6s and a real API charge on first synthesis. §14 has the numbers at scale.

09 Security architecture

  • TLS everywhere (already live via Let's Encrypt) — no plaintext ws:// in production.
  • Provider API keys (Sarvam etc.) live only in the backend's environment file — never shipped in the Android app (already true today).
  • Per-counter device tokens issued via /devices/register, required on connect; revocable without an app update.
  • Rate limiting and per-counter daily budgets enforced at the API layer (see §11) — one misbehaving device can't run up unlimited API spend.
  • Minimal retention: raw PCM audio and full transcripts are not persisted by default — only the derived analytics row (§3). If audio retention is needed for quality review, it's opt-in with a defined TTL.
  • Admin dashboard behind role-based auth; audit log for every FAQ edit/approval.

11 Failure & fallback strategy

  • Provider abstraction — SpeechToTextProvider, TranslationProvider, TextToSpeechProvider, EmbeddingProvider interfaces so Sarvam can be swapped/supplemented with Bhashini/Azure/Google via config, not a rewrite.
  • Timeouts — already 30s on the Sarvam HTTP client; add per-stage timeouts (STT/translate/TTS individually) so one slow stage doesn't stall the whole utterance.
  • Circuit breaker — trip after N consecutive provider failures, fail fast to a fallback provider or a "please ask the operator directly" message rather than hanging every subsequent request.
  • Rate limiting + daily budget — per-counter request caps and a global daily API-spend ceiling with alerting, so a stuck/looping device can't generate unbounded cost.
  • Duplicate-request suppression — identical in-flight requests from the same counter collapse to one upstream call.

13 Deployment architecture

Extends the current single-VPS deployment (187.127.167.93) rather than introducing new infrastructure: vaani-backend, a new vaani-postgres, and a new vaani-redis container on the same Docker host, all bound to 127.0.0.1 and reached only through the existing nginx vhost — consistent with how this VPS already isolates other tenants (partvik.com, evolution-api) on their own ports.

15 Performance targets & benchmarking plan

Measure each stage independently (language detection, STT, cache/intent lookup, translation, TTS, total) rather than a single end-to-end number. The Node/WebSocket timing harness already used to diagnose the audio-playback issue on this project is the starting point for a repeatable benchmark script — extend it to record per-stage timestamps from the JSON event stream and run it against a representative question set before quoting any latency figure publicly.

17 Weaknesses & mitigations

Incorrect semantic match quality

A confident-looking embedding match can still be the wrong intent, especially across dialect/code-mixed phrasing.

Mitigation: tiered confidence thresholds (§5) with a deterministic re-check in the 0.75–0.90 band, and never auto-answer emergency-category intents from semantic match alone — always route those to an operator.

Incorrect language detection

Background noise or short utterances can cause STT auto-detect to pick the wrong language, producing a fluent-sounding but wrong-language answer.

Mitigation: log detection confidence; below a floor, ask the speaker to repeat rather than answer — never silently guess.

Stale cached answers

An approved answer changes (new gate location, revised timings) but cached translations/audio still reflect the old version.

Mitigation: category + cache_policy + valid_until fields (§3); bumping faq_knowledge.version invalidates all dependent translations/audio_cache rows for that FAQ automatically.

Translation errors compounding through caching

A bad machine translation, once cached, gets served to every future pilgrim in that language until caught.

Mitigation: translation_status (machine vs. reviewed) — high-traffic FAQ answers should graduate to authority-reviewed status; dashboard surfaces per-FAQ usage volume to prioritize review.

Single external API dependency

Sarvam AI outage or rate-limiting stalls every uncached request.

Mitigation: provider abstraction (§11) makes Bhashini/Azure/Google a config change, not a rewrite; circuit breaker fails fast instead of hanging.

Network failure at the counter

Mela connectivity is inherently unreliable under crowd load.

Mitigation: offline bundle (§7) for FAQ-category questions only; clear "offline mode" UI state; queued analytics sync on reconnect.

Cost explosion from a misbehaving device

A stuck client retry-looping, or an intentionally abusive device, could otherwise run up unbounded API spend.

Mitigation: per-counter rate limits and a global daily budget ceiling with alerting (§11); duplicate in-flight request suppression.

Emergency-query mishandling safety-critical

Loose semantic matching must never generate an unverified or generic answer to a missing-child, medical, or crowd-safety query.

Mitigation: emergency category is exempt from auto-answer entirely regardless of confidence score — always transcribed, translated, and routed straight to the operator with a visible escalation flag.
